## Что это

`ragu.api` — FastAPI-сервис, который выставляет заранее построенный граф знаний
по HTTP. Он поставляется внутри пакета, поэтому установленный RAGU умеет
обслуживать граф без клона репозитория, а клиенты на любом языке могут делать
запросы вместо того, чтобы импортировать RAGU как python-библиотеку.

Сервис **обслуживает** граф и никогда его не строит. Сначала постройте граф —
`KnowledgeGraph.build_from_docs` или один из скриптов в `examples/` — затем
укажите сервису эту папку хранилища.

Один процесс владеет одним графом и выставляет по маршруту на каждый режим
поиска, чтобы шлюз мог назначить им разные таймауты и лимиты. Это важно:
глобальный поиск оценивает каждое саммари сообщества отдельным LLM-вызовом
(N+1 вызовов на N сообществ), а локальный и наивный тратят по одной генерации.

Установка с extra `api`:

```bash
pip install -e ".[api]"
```

## Запуск

```bash
# Заготовленные ответы, без графа и без LLM — для разработки клиентов
python -m ragu.api --backend stub

# Реальный граф
python -m ragu.api --backend ragu --storage-folder ragu_working_dir
```

`--host`, `--port`, `--backend` и `--storage-folder` переопределяют
соответствующие переменные окружения из командной строки. Интерактивная
документация — на `/docs`.

В Docker `docker compose up -d ragu-api` собирает образ из корня репозитория и
монтирует готовый граф в `/data/graph`. Детали развёртывания, на которых легко
обжечься — whitelist в `.dockerignore`, вшитые словари tiktoken, стартовый
период healthcheck и права записи для uid 1000 — описаны в
[`ragu/api/README.md`](../../ragu/api/README.md).

## Конфигурация

Настройки сервиса — переменные окружения `RAGU_API_*`, которые читает
`ServiceSettings` (`ragu/api/config.py`), при желании из файла `.env`.

| Переменная | По умолчанию | Значение |
|---|---|---|
| `RAGU_API_BACKEND` | `ragu` | `ragu` загружает реальный граф, `stub` отдаёт заготовленные ответы |
| `RAGU_API_HOST` | `0.0.0.0` | Адрес прослушивания |
| `RAGU_API_PORT` | `8020` | Порт |
| `RAGU_API_STORAGE_FOLDER` | `ragu_working_dir` | Папка с построенным графом |
| `RAGU_API_LANGUAGE` | `russian` | Передаётся в `Settings.language` |
| `RAGU_API_SETTINGS_FILE` | — | JSON с `Settings`, сохранённый при сборке, загружается вместо умолчаний |
| `RAGU_API_EMBEDDER_DIM` | — | Размерность эмбеддингов; без неё определяется пробным запросом |
| `RAGU_API_RATE_MIN_DELAY` | — | Минимальная задержка между LLM-вызовами, секунды |
| `RAGU_API_RATE_MAX_SIMULTANEOUS` | — | Максимум одновременных LLM-вызовов |
| `RAGU_API_LLM_CACHE` | — | Путь к кэшу ответов LLM; без него кэш выключен |
| `RAGU_API_MAX_TOP_K` | `100` | Потолок для клиентских `top_k` / `rerank_top_k` |
| `RAGU_API_MIN_CLUSTER_SIZE_FLOOR` | `1` | Нижняя граница для `min_cluster_size` глобального поиска |
| `RAGU_API_STUB_MISSING_CAPABILITIES` | — | Только для стаба: какие возможности объявлять отсутствующими |

`RAGU_API_STORAGE_FOLDER` должна указывать на одну папку графа, а не на папку с
несколькими, и эта папка обязана существовать и быть непустой — иначе сервис
откажется стартовать, а не создаст её.

Учётные данные LLM и эмбеддера берутся из того же `.env`, что и остальной RAGU
(`ragu.common.env.Env`): `LLM_MODEL_NAME`, `LLM_BASE_URL`, `LLM_API_KEY`, и
опционально `EMBEDDER_BASE_URL`, `EMBEDDER_API_KEY`, `EMBEDDER_MODEL_NAME`.

## Эндпоинты поиска

| Маршрут | Тело |
|---|---|
| `POST /v1/search/global` | `query`, `params: GlobalSearchParams` |
| `POST /v1/search/local` | `query`, `use_query_plan=true`, `params: LocalParams` |
| `POST /v1/search/naive` | `query`, `use_query_plan=true`, `params: NaiveSearchParams` |

`params` — это собственный класс параметров движка, встроенный в модель
запроса, а не переписанный поле за полем:

```json
{
  "query": "кто написал роман?",
  "use_query_plan": true,
  "params": {"top_k": 20, "rerank_top_k": null, "use_summary": true, "use_chunks": true}
}
```

Три следствия этого выбора:

- **Умолчания — движка.** Без `params` берутся `LocalParams()` /
  `NaiveSearchParams()`, то есть `use_summary` равен `false`, а `top_k` — `20`.
  Клиенту, которому это важно, следует передавать значения явно.
- **Границы — сервиса.** У датаклассов их нет, поэтому `top_k` и `rerank_top_k`
  ограничиваются сверху значением `RAGU_API_MAX_TOP_K`, а `min_cluster_size`
  поднимается до `RAGU_API_MIN_CLUSTER_SIZE_FLOOR`.
- **Неизвестные поля отвергаются — и снаружи `params`, и внутри.** И `top_k` на
  верхнем уровне (форма до появления `params`), и опечатка `params.topk` дают
  `400`, а не тихо обслуженное умолчание движка.

Глобальный поиск не принимает `use_query_plan`: его ответ синтезируется из
саммари, которые и так покрывают весь корпус, поэтому декомпозиция вопроса
привела бы лишь к повторной оценке тех же саммари на каждый подзапрос. Поле
`used_query_plan` остаётся в ответе и для этого режима всегда `false`.

Успешный ответ:

```json
{
  "query": "Кто написал роман 'Камо грядеши'?",
  "mode": "local",
  "used_query_plan": true,
  "answer": "Роман написал Генрик Сенкевич...",
  "sources": [{"id": "chunk-8f3...", "type": "chunk", "content": "...", "score": 0.87}],
  "subqueries": [{"query": "Кто написал роман?", "answer": "Генрик Сенкевич"}]
}
```

`sources` — это ретривал, разложенный в плоские `{id, type, content, score}`:
чанки и их скоры из `NaiveSearchResult`, сущности / связи / саммари / чанки из
`LocalSearchResult`, оценённые инсайты из `GlobalSearchResult`. Тип результата,
который сервис не моделирует, вырождается в один источник, отрендеренный через
`to_text()`.

Если отработал план запроса, `sources` несёт свидетельства **всех** подзапросов
без дубликатов, а не только финального: промежуточные ответы возвращаются в
`subqueries`, значит и их доказательная база возвращается вместе с ними.

## Health и readiness

| Маршрут | Статус | Назначение |
|---|---|---|
| `GET /health` | всегда `200` | Отладочный обзор; готовность — в теле ответа |
| `GET /health/live` | всегда `200` | Проба liveness: процесс жив |
| `GET /health/ready` | `200` / `503` + `Retry-After` | Проба readiness: поиск можно обслуживать |

Загрузка большого графа занимает минуты, поэтому liveness и readiness
разделены: оркестратор не должен перезапускать сервис, который ещё стартует.

```json
{
  "status": "ok",
  "graph_loaded": true,
  "stats": {"entities": 128400, "relations": 170233, "chunks": 9812, "community_summaries": 341},
  "error": null
}
```

`stats` измеряется один раз при старте, и именно из него выводится
`graph_loaded`: он означает «в графе есть что читать хотя бы одному режиму
поиска», а не «объект сконструирован». Если старт провалился, `error` несёт
причину, и та же причина попадает в тело `503` любого поиска — диагностика не
остаётся закопанной в логах.

## Ошибки

У всех ошибок один конверт:

```json
{"error": {"code": "CAPABILITY_UNAVAILABLE", "mode": "global",
           "missing_capability": "community_summaries", "message": "..."}}
```

| Статус | Код | Ситуация |
|---|---|---|
| 400 | `INVALID_REQUEST` | пустой `query`, неверный тип поля, неизвестное поле |
| 409 | `CAPABILITY_UNAVAILABLE` | граф не умеет этот режим, либо запрос ничего не нашёл |
| 503 | `SERVICE_NOT_READY` | граф не загружен или старт провалился |
| 500 | `INTERNAL_ERROR` | LLM недоступна, таймаут эмбеддера, отказ движка |

`409` существует, чтобы клиент мог среагировать сам: граф, построенный без
саммари сообществ, не ответит на глобальный поиск, а построенный без извлечения
сущностей — на локальный. `missing_capability` различает два случая `409`:

- **названа** (`community_summaries`, `entity_graph`, `vector_index`) — в графе
  нет того, что читает этот режим. Определяется по стартовому измерению,
  поэтому генерация на это не тратится.
- **`null`** — режим граф поддерживает, но конкретно этот запрос не нашёл
  свидетельств. Движки уверенно отвечают и на пустом контексте, поэтому ответ,
  построенный ни на чём, сообщается как ошибка, а не возвращается.

Ответы `500` никогда не цитируют исходное исключение: ошибки движка и
LLM-клиента регулярно содержат URL эндпоинта и куски запроса. Детали уходят в
лог сервиса.

## Проектные решения

**Почему в запрос встроен класс параметров движка.** `QueryPlanEngine`
передаёт `params` вложенному движку без изменений, поэтому опции запроса обязаны
путешествовать объектом параметров, а не аргументами конструктора.
Переиспользование тех же классов как схемы запроса означает, что параметр,
добавленный выше по стеку, доступен по HTTP без правок здесь — а
переименованный выше меняет контракт на проводе, и это цена того, что их не
переписывают заново.

**Почему возможности измеряются, а не угадываются.** Движки отвечают из любого
собранного контекста, включая пустой. Подсчёт хранилищ сущностей, чанков и
саммари один раз при старте — это то, что позволяет отказать в неподдерживаемом
режиме до оплаты генерации, и то, что делает `graph_loaded` правдивым.

**Почему конвертация диспетчеризуется по типам результата.** Движки — часть
этого же пакета и версионируются вместе с ним, поэтому `ragu/api/mapping.py`
диспетчеризуется по конкретным классам `*SearchResult`, а не прощупывает
атрибуты. Тип результата, сменивший форму, тогда падает громко, а не порождает
пустой список источников, который сервис объявил бы отсутствующей возможностью.

**Почему ручки стоимости — на стороне сервера.** Один глобальный поиск стоит
N+1 LLM-вызовов на N уцелевших сообществ. `RAGU_API_MIN_CLUSTER_SIZE_FLOOR` —
единственный ограничитель этого, как `RAGU_API_MAX_TOP_K` ограничивает ширину
ретривала; оба применяются в базовом классе бэкенда, поэтому любой бэкенд
соблюдает их одинаково.

## Логирование

`python -m ragu.api` вызывает `configure_logging` (`ragu/api/logging_setup.py`),
который ставит перехватывающий handler на корень stdlib-логирования и
переизлучает каждую запись через loguru. Uvicorn, httpx и сам сервис после
этого делят один синк и один формат с движками, поэтому один запрос
прослеживается от начала до конца. `--log-level` задаёт уровень этого синка.

Импорт `create_app` в другой сервер (gunicorn, уже настроенный uvicorn) чужое
логирование не трогает — вызовите `configure_logging` сами, если нужно такое же
поведение.

## Текущие ограничения

Известные пробелы — перечислены, чтобы их не приняли за недосмотр:

- **Один граф на процесс.** `Settings` — синглтон уровня процесса, а `Index`
  читает `Settings.storage_folder` в конструкторе, поэтому процесс обслуживает
  ровно один граф.
- **Нет ingestion по HTTP.** Сервис не умеет строить и дополнять граф;
  `build_from_docs` и CRUD-поверхность `KnowledgeGraph` наружу не выставлены.
- **Только поиск, по одному запросу за раз.** `MixSearchEngine`, ретривал без
  генерации (`batch_search`), батчевые запросы (`batch_query`) и стриминг
  (`stream_query`) движками поддержаны, но пока не выставлены.
- **Нет аутентификации, квот и метрик.** Каждый запрос стоит LLM-вызовов;
  ставьте сервис за шлюз, который аутентифицирует и ограничивает частоту.
